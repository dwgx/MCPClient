# Code Review — 双轴审查

灵感来自 mattpocock/skills 的 code-review(两轴 + 并行 subagent)。本项目对安全内核尤其要严。

## 什么时候用

- 任何代码改动完成后、宣布"做完了"之前。
- 合并、提交前(配合铁律#2:先编译再测才提交)。
- 动到冻结契约 / 7 层安全内核 / ProtectedClasses 之前必须跑,且升级到对抗性复查。

## 两根轴(分开审,别混)

**标准轴(怎么写的)**
- 正确性:边界条件、空值、并发、资源泄漏(本项目 Board 踩过订阅泄漏、CME)。
- 安全:输入校验、常量时间比较(token/HMAC)、门控是否绕得过、TOCTOU。
- 风格:跟周围代码一致,不引入新库/新模式;无 emoji(注释/代码内一律禁)。
- 简约(Karpathy):每一行都能追溯到需求;200 行能写成 50 就重写。**但**安全内核的
  防御性代码是必需的,不适用"删掉不可能情况的处理"——见 external-doctrine.md 的调校记录。

**规格轴(做没做对事)**
- 回到原始需求:要求的每一点都实现了吗?有没有多做(scope creep)?
- 有没有"外科手术"以外的顺手改动(drive-by refactor)?本项目禁。
- client 是否仍纯 vanilla?`_*` 参考代码有没有污染 target?
- 配套的非空转回归测试写了吗(旧代码上会失败那种)?

## 怎么做

1. 大改动:派两个 subagent,一个只走标准轴、一个只走规格轴,并行,各自出结构化发现清单。
2. 小改动:自己顺两轴过一遍。
3. 发现按严重度排序(critical/high/med/low),critical 必须挡在提交前。
4. 复查通过 = 编译绿 + 测试绿 + 两轴无 critical。

## 铁规矩

- 别把"减速带当城墙"吹——诚实报告没盖住的边界。
- 找不到问题不等于没问题;安全类默认"有罪推定",逼自己构造失败场景。
