# 00-META — 项目北极星与元架构

## 北极星(一句)

一个**系统级架构,驱动对活着的 Minecraft 1.8.9 Java 进程能做的一切**——观察、反射、
挂载(hook)、热改(hot-swap)每一个游戏方法与整个运行中的 JVM,把跑着的游戏变成一块
完全可控、可编程的基底。

**MCP / 把控制暴露给 LLM 是这个基底最重要的驱动入口(因为是 AI 时代),但不是本质。**
本质是"系统级完全控制活体游戏进程";AI 只是驱动它的旗舰方式——控制面原则上也可由脚本 /
GUI / 直接 API 驱动。

> 别把项目定义成"AI 控制 MC"——那是旗舰功能,不是本质。本质是"对活 JVM 的系统级控制"。

## 四个关注点(关键:不全在一个哲学下)

```
① 控制(核心能力)──────────────────── 项目本质
   反射 / hook / hot-swap / seam over 活 JVM
   = core(NT分层) + client(vanilla映射=反射基准) + board + lwjgl2-shim
        │
        ├── ② 暴露(AI时代的功能,非本质)
        │      MCP server + REST facade 把控制面给 LLM
        │
   ┌────┴──────────────────────────────┐
   │                                     │
 ③ 信任(统一在一个哲学下)         ④ 自我保护(独立,正交)
 "LLM 三重身份"                     抗逆向加固
 · 权限内核(治"用户LLM")           · 对手 = 任何逆向者(人/LLM)
 · 补丁签名(信"可信补丁")          · 架构级墙 / 移动目标 / 买时间
 · 文档治理(可信交接给"建造者LLM") · 用自己的原理,保护 ①②③
 —— 管"系统的行为"                  —— 管"系统的形态"
    (行为轴 / 内部治理)                (形态轴 / 外部加固)
```

### ① 控制(核心能力)= 项目本质
反射 / hook / hot-swap / seam over 活体 JVM。承载:`core`(NT Executive 分层)+
`client`(vanilla 映射,是反射/GUI 字段名的**基准真相**)+ `board` + `lwjgl2-shim`。
回答"我们能对游戏做什么"。

### ② 暴露(AI 时代的功能,非本质)
MCP server(socket 25599)+ REST facade(1337)把控制面暴露给 LLM。是旗舰用途,不是本质。
细节见 `02-CAPABILITIES.md`。

### ③ 信任(统一在一个哲学下)—— "LLM 三重身份"
因为 LLM 在本项目里同时是**建造者**(写 core/board 的是 LLM)、**用户**(控制面暴露给 LLM)、
**威胁**(可能越权 / 伪造补丁 / 敌对)。所以需要:
- **权限内核**(治"用户 LLM":7 层 / R-1 / generated 顶格 gate)→ `01-SECURITY-KERNEL.md`
- **补丁签名**(只信"可信补丁":compat 的 **Ed25519 验签 + TUF 信任链**;旧稿写"HMAC"是 07-13 加密线落地前的过时说法)→ `07-COMPAT-SHIM.md`
- **文档治理**(可信交接给"建造者 LLM":三层锁 / doc_lint / codegraph)→ `ARCHITECTURE-LOCK.md`、`../reference/codegraph.md`

这三者统一回答**一个**问题:**在 LLM 既是建造者、又是用户、又是威胁的世界里,如何构建可信的控制。**
它们管的是**系统的行为**(做什么 / 谁驱动 / 怎么治理)——**行为轴 / 内部治理**。

### ④ 自我保护(独立、正交)—— 抗逆向加固
把编译产物加固到难以逆向。**对手是任何逆向者(人或 LLM),不只 MCP 里的用户 LLM。**
用它自己的原理(架构级墙 / 移动目标 / 买时间,见抗-LLM 混淆研究),服务于保护 ①②③,
但**不属于**信任哲学。它管的是**系统的形态**(从外面多难读懂)——**形态轴 / 外部加固**。
承载:第 5 模块 **`pg`**(PatchGuard 加固库,`@Guarded` 标注驱动的字节码加固;`pg-api`/`pg-engine`/`pg-maven-plugin`)——独立于 ①②③ 的模块,故意不在 ① 控制的模块列里。见 `../design-briefs/pg-hardening-lib-design.md`。

## 为什么 ③ 能统一而 ④ 必须独立(这条分界别忘)

- ③ 信任管"系统**做什么**、谁能驱动、怎么治理"= **行为轴 / 关系问题**。
- ④ 混淆管"编译产物从**外面**多难读懂"= **形态轴 / 不透明问题**。
- **行为 vs 形态是两根不同的轴。** 硬把混淆并进"信任哲学"会把两边都搅浑——所以混淆是
  第四个、独立的关注点。它保护前三层,但不共享它们的哲学。

## 这张图怎么用(接手者一句话定位)

- 在做反射 / hook / 热改? → ① 控制
- 在做 MCP 工具 / 暴露? → ② 暴露
- 在做权限 / 签名 / 文档治理? → ③ 信任(归一个哲学)
- 在做混淆 / 抗逆向? → ④ 自我保护(独立,别当成信任的一部分)
